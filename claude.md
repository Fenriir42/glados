# CLAUDE.md - Project Memory & Development Guidelines

## Project Overview

- **Name:** Glados
- **Core Stack:** Haskell, GHC, Stack / Cabal
- **Type:** Custom programming language compiler/interpreter toolchain.
- **Current Development Phase:** Implementation of the bytecode generation architecture, Virtual Machine (VM) execution loop, and expansion of the language's native standard library (written in our own language).

---

## Architectural Layout

- **Frontend:** Lexer, parser, and abstract syntax tree (AST) structures are mature. Do not refactor unless explicitly instructed.
- **Backend / Code Gen:** Translates the existing AST/IR into a custom bytecode instruction set.
- **Runtime:** A virtual machine that loads, evaluates, and manages the execution environment for the generated bytecode.
- **Standard Library:** Native scripts/modules written in the custom language to provide foundational operations.

---

## Development & Build Commands

Always use the following commands to build, test, and maintain the project environment:

- **Build the Project:** `cabal build`
- **Run the Compiler:** `cabal run`
- **Execute Unit Tests:** `cabal test`
- **Interactive REPL:** `cabal ghci`
- **Format Code:** `fourmolu --mode inplace .` or `ormolu --mode inplace $(find . -name "*.hs")`

---

## Technical & Style Constraints

### 1. Pure Functional Haskell Style

- Prefer pure functions over heavy reliance on the `IO` monad wherever possible.
- Use explicit, strong algebraic data types (ADTs) for the Bytecode instruction set architecture (ISA).
- Keep data types clean and descriptive; separate the definition of data structures from their evaluation engines.

### 2. Error Handling

- Do not use partial functions like `head`, `tail`, or `undefined` in new code.
- Leverage the `Either` monad, custom error variants, or MonadError type classes to gracefully cascade and format compiler/runtime errors.

### 3. Bytecode & VM Design Focus

- Ensure the instruction set architecture remains minimal, highly decoupled, and easy to interpret.
- Explicitly trace register allocations, stack states, or environment bindings during bytecode evaluation.

### 4. Commits

- NEVER put yourself as the co-author

### 5. Misc

- do not use em dashes (—)
