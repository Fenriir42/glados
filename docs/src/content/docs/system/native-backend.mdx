Quant programs normally run on the bytecode VM. The native backend instead
translates the compiled bytecode to C and hands it to the system C compiler,
producing a standalone optimized binary.

## Compiling a file

```bash
glados compiler program.qa --native ./program
./program
```

The generated C is kept next to the binary (`./program.c`) for inspection.
To only generate the C without compiling it:

```bash
glados compiler program.qa --emit-c program.c
```

## Compiling a project

```bash
glados build --target c
./.build/main
```

## How it works

Each bytecode function becomes one C function over the runtime's `QtValue`
type; the VM's operand stack becomes a local array, jumps become `goto`
labels, and calls to your functions become direct C calls. The binary links
against a small C runtime (`quant_runtime.c`) that reproduces the VM's value
semantics exactly -- including printing formats, so VM and native output can
be diffed byte-for-byte.

The binary is built with `-O2 -flto` (float results stay bit-identical --
no `-ffast-math` or `-march=native`), so the small runtime value accessors
inline into the generated hot paths. The speedup is substantial: the
`benchmarks/` suite (`make bench`, which checks output parity before timing)
measures roughly **63x** on recursion (`fib`), **94x** on nested integer
loops, and **109x** on prime counting versus the VM.

## Checking native output against the VM

The `native-diff` subcommand is the backend's safety net. It runs every
`.qa` file under both engines and diffs stdout and exit codes:

```bash
glados native-diff            # defaults to tests/
glados native-diff my_dir a.qa
```

Each file is reported as one of:

- `ok` -- VM and native output are byte-identical (including exit code).
- `skip` -- the translator does not cover the file yet (the unsupported
  instruction or builtin is named), or the file does not compile
  standalone. Unsupported programs are rejected at compile time, so a
  skip can never hide a behavioral difference.
- `DIFF` -- the two engines disagree; the first differing line is shown.
  This always indicates a bug and fails the run with exit status 1.

The harness runs in CI on every pull request, so any change to the
compiler, VM, or C runtime that makes the two engines disagree is caught
immediately.

<Aside type="caution">
The native backend currently covers a broad subset of the language:
functions, recursion, control flow, int/float/bool/string scalars, arrays,
dicts, structs, enums, error/option values (`try`/`must`), interfaces with
dynamic method dispatch, closures and first-class functions, `extern` FFI
calls (via `dlopen`, including callbacks of any arity 0-4 with pointer args
and int-class return, e.g. `qsort` and `qsort_r`), raw pointers,
casts, the printing builtins, and the full `string.*` (except `hash`),
`math.*`, `sys.*`, `file.*`, `buf.*`, `ptr.*`, `socket.*`, and `dict.*`
builtin families, and async `spawn`/`await` (a cooperative `ucontext`
scheduler). The only builtins left untranslated are `json.*`, `regex.*`, and
`string.hash` -- each would have to reproduce a specific Haskell library's
exact byte output or semantics (aeson, regex-tdfa, unbounded-`Integer`
hashing), which can't be matched in C, so programs using them fail at
compile time rather than silently diverging. See ROADMAP.md.

A program whose output is inherently non-deterministic (external network,
wall-clock, randomness) cannot be compared byte-for-byte; mark it with a
`// native-diff: skip` comment and the harness reports it as a skip rather
than running it.
</Aside>

## Environment

| Variable | Meaning |
|----------|---------|
| `QUANT_RUNTIME_DIR` | Directory containing `quant_runtime.{c,h}` (default: `./runtime`, then `/usr/local/share/quant/runtime`) |
| `QUANT_CC` | C compiler to invoke (default: `cc`) |
