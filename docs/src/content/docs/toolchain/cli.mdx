The `glados` binary is the whole Quant toolchain: a compiler/runner for single
files, a project manager, a test runner, a formatter and linter driver, and a
native-binary builder. It comes in **two layers**:

- **`glados compiler`** works on a *single source file* -- no project needed.
- Every other subcommand (`build`, `run`, `test`, `watch`, ...) works on a
  *project*: a directory with a `quant.toml` manifest.

<Aside type="tip" title="The mistake everyone makes first">
`glados compiler` takes **one source file, given first**, and `--native`
names the *output binary*:

```bash
glados compiler src/main.qa --native ./hello   # correct
glados compiler --native hello                 # wrong: no source file
glados compiler src/ --native hello            # wrong: not a single file
```

To build a whole project instead, use `glados build --target c` (below).
</Aside>

## Single files: `glados compiler`

```
glados compiler [FILE] [--dump] [--output FILE] [--load FILE]
                [--stdlib DIR] [--native BIN] [--emit-c FILE]
```

| Invocation | What it does |
|------------|--------------|
| `glados compiler prog.qa` | Compile and **run** `prog.qa` on the bytecode VM |
| `glados compiler prog.qa --dump` | Print the bytecode disassembly instead of running |
| `glados compiler prog.qa --output prog.qbc` | Write compiled bytecode to a `.qbc` file |
| `glados compiler --load prog.qbc` | Load and run a pre-compiled `.qbc` file |
| `glados compiler prog.qa --native ./prog` | Compile to a **standalone native binary** at `./prog` (via the C backend) |
| `glados compiler prog.qa --emit-c prog.c` | Emit the generated C without compiling it |
| `glados compiler prog.qa --stdlib DIR` | Use a specific standard-library directory |

The native backend links against a small C runtime; see
[Native Backend](/system/native-backend/) for details and the
`QUANT_RUNTIME_DIR` / `QUANT_CC` environment variables.

## Projects

A project is any directory containing a `quant.toml` manifest:

```toml
[project]
name    = "my-project"
version = "0.1.0"
entry   = "src/main.qa"
```

### `glados init NAME [--ci github]`

Scaffold a new project in a directory `NAME`: creates `quant.toml`, a
hello-world `src/main.qa`, and a `tests/main_test.qa`.

```bash
glados init hello
cd hello
glados run
```

With `--ci github`, it also writes `.github/workflows/quant.yml` -- a GitHub
Actions workflow that runs `glados build`, `glados test`, `glados lint`, and
`glados fmt --check` on every push and pull request:

```bash
glados init hello --ci github
```

The workflow includes a commented placeholder for installing the Quant
toolchain (a release `.deb`, a Nix build, or building from source) so the
`glados` commands are on `PATH`.

### `glados build [--release] [--target c]`

Compile the entry point. By default writes bytecode to `.build/main.qbc`.
With `--target c`, translate the compiled bytecode to C and produce a
**native binary** at `.build/main` (the generated C is kept at
`.build/main.c`):

```bash
glados build              # -> .build/main.qbc  (bytecode)
glados build --target c   # -> .build/main       (native binary)
./.build/main
```

<Aside type="note">
`glados build --target c` is the project-level equivalent of
`glados compiler <entry> --native <out>`. Use `build` for projects,
`compiler --native` for one-off files.
</Aside>

### `glados run`

Compile the entry point and immediately execute it on the VM.

### `glados test [FILE] [--cov] [--cov-min PCT] [--cov-out FILE]`

Discover and run every `*_test.qa` file under the test directory. Any
parameterless function named `test_*` is a test case; use the
`assert`/`assert_eq`/`assert_ne`/`assert_true`/`assert_false`/`assert_panic`
builtins inside them.

```bash
glados test                 # run all tests
glados test tests/foo_test.qa   # run one file
glados test --cov           # print function/line/branch coverage
glados test --cov-min 80    # fail if function coverage < 80%
glados test --cov-out cov.json   # write a JSON coverage report
```

### `glados bench [FILE]`

Discover and run microbenchmarks. Without an argument it scans
`benchmarks/` and the test directory for `*_bench.qa` files; with a `FILE`
it runs just that one. Every parameterless `bench_*` function is executed,
and inside it you call `bench_fn` from the `bench` standard-library module
to time a closure across several samples:

```quant
from bench import bench_fn

fn fib(n: int) -> int {
    if (n < 2) { return n; };
    return fib(n - 1) + fib(n - 2);
}

fn bench_fib20() -> void {
    bench_fn("fib(20)", 50, fn() -> void { fib(20); });
}
```

```bash
glados bench benchmarks/fib_bench.qa
# ok bench fib(20): 50 iters/sample, 17531061 ns/op (+/- 220076)
```

`bench_fn` reports throughput (`ns/op`) and a standard deviation across
samples, in a TAP-compatible line. (This is distinct from `make bench`,
which times the whole VM against the native backend.)

### `glados watch [CMD...]`

Re-run a subcommand whenever a `.qa` file under `src/` or the test directory
changes -- the fast inner dev loop. `CMD` defaults to `build`, and any flags
are forwarded to it. Runs once at startup and then after every change;
Ctrl-C stops.

```bash
glados watch                # rebuild on every save
glados watch test           # re-run the test suite on every save
glados watch test --cov     # ...with coverage
glados watch run            # recompile and re-run the program
```

<Aside type="note">
The watcher polls file modification times (~400 ms), so it has no native
dependencies and works the same on every platform.
</Aside>

### `glados fmt [--check]`

Format all source files with the comment-preserving formatter. With
`--check`, exit non-zero if any file would change (useful in CI):

```bash
glados fmt            # rewrite files in place
glados fmt --check    # CI gate: fail if anything is unformatted
```

### `glados lint`

Run the `wheatley` linter over all project sources (unused variables,
unreachable code, missing returns, naming conventions, and more).

### `glados doc [--format html|md] [--out DIR]`

Generate API documentation from `//` doc comments above `fn`, `struct`, and
`error` declarations. Defaults to HTML in `docs/api/`.

### `glados clean`

Remove build artefacts (the `.build/` directory).

## Verifying the native backend: `glados native-diff [PATH...]`

Runs every `.qa` file (default: `tests/`) under **both** the bytecode VM and
a freshly built native binary, then diffs their stdout and exit codes. It is
the backend's correctness gate -- if the two engines ever disagree, it fails.

```bash
glados native-diff            # check tests/
glados native-diff examples/  # check another directory
```

Each file is reported as `ok` (byte-identical), `skip` (not translatable
yet, or annotated non-deterministic), or `DIFF` (a real mismatch). A program
whose output is inherently non-deterministic (network, wall-clock,
randomness) can opt out with a `// native-diff: skip` comment. See
[Native Backend](/system/native-backend/).

## Fuzzing the backend: `glados fuzz [--seed N] [--count N]`

Where `native-diff` checks a fixed corpus, `glados fuzz` *generates* it. It
produces random, type-correct, terminating Quant programs from a seeded
generator (arithmetic, comparisons, strings, control flow, non-recursive
functions) and runs each under both engines, flagging any divergence in
stdout or exit code. Because generated programs are deterministic, any
divergence is a real bug.

```bash
glados fuzz --count 200          # 200 programs from seed 1
glados fuzz --seed 500112 --count 1   # reproduce one reported case
```

Each failing case prints its seed, so it reproduces in one line. This is how
the `-0.0` formatting bug (the VM dropped the sign of negative zero) was
found and fixed.

## Stress-testing your program: `glados panik`

Where `fuzz` tests *the backend*, `panik` tests *your program*. It is an
AFL-style input stress tester: it compiles the project to a native binary and
then throws a crapload of generated argument vectors at it, concurrently,
hunting for three things:

- **crashes** -- the binary dies on a signal (segfault, abort, `SIGFPE`, ...);
- **hangs** -- a run exceeds the timeout;
- **oracle violations** -- with the validity oracle, inputs the program
  wrongly *accepts* (exits 0 on out-of-spec input) or wrongly *rejects*
  (exits non-zero on in-spec input).

The argument contract lives in a `[panik]` section of `quant.toml`:

```toml
[panik]
batch      = 1000       # total runs
jobs       = 8          # concurrency (default: CPU count)
timeout_ms = 2000       # a run slower than this counts as a hang
swap       = false      # if true, argument positions may be permuted
invalid    = 0.25       # fraction of runs fed deliberately out-of-spec args
# One entry per positional argument, on a single line (TOML inline array):
args = ["int:1..100", "choice:easy,hard", "str:0..20", "bool"]
```

Each `args` entry is a compact type spec:

| Spec | Generates |
|------|-----------|
| `int` / `int:LO..HI` | an integer (optionally range-bounded) |
| `float` / `float:LO..HI` | a floating-point number |
| `str` / `str:MIN..MAX` | a printable string of length in the range |
| `choice:a,b,c` | one of the listed literal values |
| `bool` | `true` or `false` |

```bash
glados panik                       # run the [panik] batch
glados panik --batch 5000 --jobs 16   # override config from the CLI
glados panik --seed 42             # reproduce a specific run set
```

`panik` exits non-zero if it finds any crash, hang, or oracle violation, and
prints a copy-pasteable command line for each finding so it reproduces
immediately. A worked example lives in
[`examples/panik-demo/`](https://github.com/Sigmapitech/glados/tree/main/examples/panik-demo).

<Aside type="note">
`panik` builds through the C backend, so the program must be
native-translatable (the same subset `native-diff` covers). Its inputs arrive
as `sys.args()` -- which does **not** include the program name: `sys.args()[0]`
is the first real argument and `sys.argc()` counts only real arguments.
</Aside>

## Other binaries

The toolchain installs a few companion binaries that the subcommands above
dispatch to, and which you can also run directly:

| Binary | Purpose |
|--------|---------|
| `quant-lsp` | Language server (diagnostics, hover, completion, ...) |
| `quant-fmt` | The formatter (`glados fmt` wraps it) |
| `wheatley` | The linter (`glados lint` wraps it) |
| `quant-dap` | Debug Adapter Protocol server for step debugging |
| `glados-repl` | Interactive REPL |

Each ships with a man page (`man glados`, `man quant-lsp`, ...).
